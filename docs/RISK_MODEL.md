# Payment risk model

This is the model card for `aasthi-payment-risk v1`: what it is, what it was
trained on, what it scored on data it never saw, and what it is not allowed to
do.

## Why it exists separately from the rules

The rail has screened UPI Collect payments since the first week, with
hand-written rules: amount bands, velocity counts, a structuring window, a
small list of suspicious VPA fragments. Those rules are useful, fast and fully
explainable, and they are not machine learning. For a while the code described
them as an "ML-pluggable" interface, which is the sort of phrasing that lets a
reader hear "AI" without anything having been trained. That wording is gone.

What replaces it is an actual trained classifier, fitted in this repository,
with its coefficients committed to source control and its measurements
published next to them. The rules still decide. The model is a second opinion
that has to show its working.

## What it is

A logistic regression over ten features, fitted by batch gradient descent with
L2 regularisation. Ten coefficients, one bias, one mean and one standard
deviation per feature. Inference is a dot product: microseconds, no service
call, no key, nothing to be unavailable.

Linear and small is a choice, not a limitation we are apologising for. A
gradient-boosted tree would score a little better and would not be able to tell
a payer in one sentence why their payment was flagged. Every score this model
produces comes back with the features that moved it and by how much.

## What it was trained on

**Synthetic data. 12,000 generated payments, 70/30 split.**

Nobody has given this project labelled payment fraud. Real labels come from
banks and they do not leave banks. So the training set is generated by a seeded
program in the repository rather than collected, and every surface that reports
a metric says so: the model card endpoint, the weights file, the code comments
and this page.

The generator builds two overlapping populations:

- Ordinary payments: amounts clustered around a personal norm, one or two
  payments in a day, verified identity, daytime, an account that has existed
  for a while.
- Fraudulent shapes drawn from what investigators describe: amounts parked just
  under a reporting threshold, repeated near-identical amounts, bursts of
  payments within minutes, large sums from accounts minutes old, activity
  between midnight and five in the morning.

Two deliberate contaminations keep the problem honest. Roughly a fifth of the
fraudulent payments are careful enough to look ordinary, and a tenth of the
ordinary ones carry a shape that looks wrong (a property purchase against a
quiet history, a new account buying in). Two percent of labels are flipped,
because real fraud labels are decided by tired people reading incomplete files.

Without that contamination the model scored a held-out AUC of 1.000, which does
not mean it was good. It means the generator was separating the classes on the
model's behalf. A clean 1.000 in a report like this should always be read as a
defect in the evaluation.

## Features

| Feature | Meaning |
| --- | --- |
| `log_amount` | log of the payment amount in rupees |
| `amount_vs_recent_mean` | this amount over the payer's recent average, capped at 10 |
| `txn_count_10m` | payments by this payer in the last ten minutes |
| `txn_count_24h` | payments by this payer in the last day |
| `log_total_24h` | log of the payer's rupee total over the last day |
| `log_account_age_min` | log of the account age in minutes |
| `kyc_verified` | 1 when KYC is complete |
| `near_threshold` | how far under a 50k / 2L / 10L reporting line the amount sits, 0 to 1 |
| `repeat_amount_share` | share of recent payments within five percent of this amount |
| `odd_hour` | 1 when the payment lands between midnight and five, Indian time |

Training and inference call the same extraction function. A feature computed
one way during training and another way in production is the most common way a
model quietly stops working, so there is only one implementation of it and a
test asserts the weights file and the extractor agree on the order.

## Measured results

Held out, on rows the fit never saw, with the operating threshold chosen on the
training split only:

| Metric | Value |
| --- | --- |
| AUC | 0.824 |
| Accuracy | 0.860 |
| Precision | 0.626 |
| Recall | 0.719 |
| F1 | 0.670 |
| Held-out rows | 3,600 |
| Base rate | about 18 percent |

Read that honestly. Catching roughly seven in ten of the generated fraud at
about six in ten precision is a useful second opinion and nothing like a
finished anti-fraud system. It is also a number about the generator, not about
Indian payments.

The live figures are served from the weights file rather than copied by hand,
so this table cannot drift away from the model without a test noticing.

## What it is not allowed to do

- **It does not decide.** The published rules make the call. The combined
  assessment returns both scores and labels the agreement between them, which is
  the case a reviewer most needs to see: the payments where the two differ.
- **It does not block anybody's money.** A model trained on invented data
  stopping a real settlement would be indefensible.
- **It does not see anything beyond the payment and the payer's recent
  history.** No identity attributes, no geography, no device, no counterparty
  profile.

## Retraining

```
cd drunix-gateway
go run ./cmd/trainrisk          # rewrites riskmodel.json
go test ./...                   # the model tests run against the new weights
```

The seed is fixed, so a rerun on the same code produces the same file. Changing
the generator, the features or the hyperparameters changes the weights and the
published metrics together: the numbers on this page come from the same run
that produced the coefficients, and there is no path by which one can be
updated without the other.
