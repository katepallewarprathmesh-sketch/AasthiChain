Solution — Tokenization on Drunix + UPI Collect Settlement (INR) + Atomic DvP

Core Narrative: Tokenized real-asset ownership on Drunix + payment settlement modeled on NPCI's UPI/IMPS rails.

Flow: Originator registers property (title, location, valuation, documentHash auto SHA-256) → Registrar validates DRAFT→VALIDATED → Mint dual endorsement AND(Originator, Registrar) → 15000 tokens @ ₹500 for ₹75L property → Investor sees marketplace → PRIMARY PAYMENT: Originator (payee) initiates UPI Collect P2M: originator@aasthichain requests ₹2.5L from investor@aasthichain via NPCI switch mock → payer receives collect notification → approves in UPI app → backend checks KYC (DigiLocker mock) + balance (mock UPI account) → CONFIRMED → webhook callback → calls Drunix TransferTokens → 500 tokens move → RELEASED → IMPS UTR credited to payee → atomic DvP (money + tokens move together or both refunded). INR stored as paise int64 to avoid float.

Why UPI Collect P2M (not Intent)? Real estate: seller requests payment, buyer approves — matches merchant collect flow, gives seller control + UPI mandate, settlement via IMPS gives UTR for reconciliation (NPCI pattern). Intent would be buyer-initiated direct pay — less control for seller. For high-value real estate, collect with approval is more auditable.

Primary Rail — UPI Collect + IMPS

VPA: investor@aasthichain, originator@aasthichain validated via regex ^[a-z0-9._-]{2,64}@[a-z0-9]{2,64}$
IDs: PaymentID NPCI-XXXXXXXXXXXX, UPI Txn ID AASTYYYYMMDDXXXXXXXX (35-char), RRN 12-digit 418... (Retrieval Reference Number), UTR IMPS418...+4-digit (IMPS settlement ref)
Flow: PENDING (5 min expiry) → CONFIRMED (KYC+balance ok) → RELEASED (after Drunix TXN) / REFUNDED (if Drunix fails) — atomic DvP
Idempotency: X-Idempotency-Key header → same paymentId, no double-charge, file-backed per Track A4
Failure modes: insufficient funds, KYC unverified, timeout, declined, invalid VPA, duplicate idempotency — 6 payment failure modes demoable

Endorsement Policies + Atomic DvP

  • Mint: AND('OriginatorMSP.peer','RegistrarMSP.peer') — dual
  • Transfer: Investor only, KYC VERIFIED check, plus payment CONFIRMED check
  • Payment: PENDING→CONFIRMED→RELEASED/REFUNDED — same state machine as Solidity escrow but INR
  • Regulator: non-endorsing observer, privacy no PII on-chain, can freeze + audit UTRs
  • Composite keys: balance~assetId~ownerId
  • Idempotency: file-backed survives restart A4 + X-Idempotency-Key for payments
  • Atomic DvP: If Drunix TransferTokens fails, payment REFUNDED — no partial state
